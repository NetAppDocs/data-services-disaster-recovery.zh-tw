= 了解NetApp Disaster Recovery
:hardbreaks:
:allow-uri-read: 
:icons: font
:imagesdir: ../media/get-started/


[role="lead"]
雲端災難恢復是一種具有恢復能力的且具成本效益的方式，可保護工作負載免受站台中斷和資料毀損事件的影響。NetApp Disaster Recovery 是一項雲端型的災難恢復服務，可為執行 NetApp 儲存設備的 VMware 和 Kubernetes 工作負載自動執行災難恢復工作流程。透過災難恢復，您可以保護下列工作負載：

* *VMware 工作負載*：基於 NFS 的工作負載，以及適用於 iSCSI 和 FC 的 VMware vSphere 虛擬機器檔案系統（VMFS）資料儲存。您可以將其複寫到下列其中一項：
+
** Amazon Elastic VMware Service (EVS) 與 Amazon FSx for NetApp ONTAP。如需詳細資訊，請參閱 link:../reference/evs-deploy-guide-introduction.html["使用 Amazon Elastic VMware Service 和 Amazon FSx for NetApp ONTAP 進行災難恢復簡介"]。
** AWS 上的 VMware Cloud (VMC) 以及適用Amazon FSx for NetApp ONTAP
** Azure VMware Solution 與 NetApp Cloud Volumes ONTAP (iSCSI)（私有預覽版）
** Google Cloud VMware Engine (GCVE) 與Google Cloud NetApp Volumes
** 另一個採用本地 NFS 和/或 VMFS （iSCSI/FC） 的 VMware 環境，配備 ONTAP 儲存設備


* *Kubernetes 工作負載*：在您的內部部署 Kubernetes 叢集（包括 OpenShift 虛擬化環境）上執行，且使用 Trident 管理的 ONTAP 儲存設備的應用程式。您可以使用 Trident Protect 保護它們，並將其複寫到另一個 Kubernetes 叢集。


災難恢復採用 ONTAP SnapMirror 技術，並整合原生 VMware 協調或 Trident Protect 協調，以保護 VMware 虛擬機器及其關聯的磁碟作業系統 "映像" 和 Kubernetes 應用程式，同時保留 ONTAP 的所有儲存效率優勢。災難恢復使用這些技術作為到災難恢復站台的複寫傳輸方式。這使得主要和次要站台都能實現業界最佳的儲存效率（壓縮和重複資料刪除）。

[[netapp-console]]
== NetApp Console

可透過 NetApp Console 存取災難恢復。

NetApp Console提供企業級跨本機和雲端環境的NetApp儲存和資料服務的集中管理。需要控制台才能存取和使用NetApp資料服務。作為管理介面，它使您能夠從一個介面管理許多儲存資源。控制台管理員可以控制企業內所有系統的儲存和服務的存取。

您無需授權或訂閱即可開始使用 NetApp Console，只有當您需要在雲端部署 Console 代理程式以確保與儲存系統或 NetApp 資料服務的連線時才會產生費用。但是，某些可從 Console 存取的 NetApp 資料服務需要授權或訂閱。

詳細了解 https://docs.netapp.com/us-en/console-setup-admin/concept-overview.html["NetApp Console"]。



[[benefits-of-using-disaster-recovery]]
== 使用災難恢復的效益

災難恢復提供以下優勢：

* 簡化 vCenter 和 Kubernetes 叢集探索與應用程式恢復的使用者體驗，並支援多個時間點恢復操作。
* 透過降低營運成本來降低整體擁有成本，並能夠以最少的資源創建和調整災難復原計劃。
* 透過虛擬故障轉移測試持續做好災難復原準備，不會中斷營運。您可以定期測試 DR 故障轉移計劃，而不會影響生產工作負載。
* 透過 IT 環境的動態變化和在災難復原計劃中解決該問題的能力來更快地實現價值。
* 能夠透過ONTAP和 VMware 的後端編排同時管理儲存層和虛擬層，而無需部署和維護虛擬伺服器設備 (VSA)。
* 使用相同的 ONTAP SnapMirror 技術與 Trident Protect 協調，為 Kubernetes 工作負載提供以應用程式為中心的保護。資源轉換可讓您在容錯移轉期間，將工作負載調整至恢復環境。
* VMware 的 DR 解決方案可能會佔用大量資源。許多 DR 解決方案使用 VSA 在 VMware 虛擬層複製虛擬機，這會消耗更多的運算資源並損失ONTAP寶貴的儲存效率。由於災難復原使用ONTAP SnapMirror技術，它可以使用我們的永久增量複製模型將資料從生產資料儲存複製到 DR 站點，並具有ONTAP的所有本機資料壓縮和重複資料刪除效率。




[[capabilities-of-disaster-recovery]]
== 災難恢復能力

災難恢復使您能夠充分利用多種 NetApp 技術來實現以下目標：

* 使用SnapMirror複製將本地生產站點上的 VMware 應用程式複製到雲端或本地端的災難復原遠端站點。
* 使用 SnapMirror 複寫和 Trident Protect 將 Kubernetes 應用程式複寫到目的地 Kubernetes 叢集。
* 將 VMware 工作負載從原始站台遷移到另一個站台。目前不支援 Kubernetes 工作負載的遷移。
* 執行容錯移轉測試。對於 VMware 工作負載，此服務會建立暫時的虛擬機器。災難恢復會從選定的快照建立新的 FlexClone Volume，並將由 FlexClone Volume 支援的暫存資料存放區對應至 ESXi 主機。此程序不會使用內部部署 ONTAP 儲存設備或 AWS 中 FSx for NetApp ONTAP 儲存設備的額外實體容量。原始來源 Volume 不會被修改，即使在災難恢復期間，複本作業也可以繼續進行。您也可以測試 Kubernetes 工作負載的容錯移轉，並在之後清理測試資源。
* 發生災難時，可隨需將主站台容錯移轉至災難恢復站台。對於 VMware 工作負載，災難恢復站台可以是搭配 Amazon FSx for NetApp ONTAP 的 VMware Cloud on AWS，或是搭配 ONTAP 的內部部署 VMware 環境。對於 Kubernetes 工作負載，您可以容錯移轉至複寫計畫中的目的地叢集。
* 災難解決後，根據需要從災難復原站點故障回復到主站點。
* 將虛擬機器、資料儲存或 Kubernetes 資源分組到邏輯資源群組中，以便進行高效管理。
* 對於 Kubernetes 工作負載，使用資源轉換使應用程式在容錯移轉期間適應恢復環境，並使用快照前或快照後指令碼來管理應用程式的靜止與恢復。


image:../use/evs-use-cases.png["顯示災難恢復使用案例的圖表"]


NOTE: 對於 VMware 工作負載，您必須在 vSphere 伺服器中的災難恢復之外設定 vSphere 伺服器。

[[licensing]]
== 授權

您可以使用以下許可證類型：

* 註冊 30 天免費試用。
* 您可以透過 Amazon Web Services （AWS） Marketplace、Azure Marketplace 或 Google Cloud Marketplace 購買隨用隨付 （PAYGO） 訂閱。此授權可讓您購買固定的受保護容量授權，無需任何長期承諾。
* 自帶授權 (BYOL)，即您從NetApp銷售代表取得的NetApp授權文件 (NLF)。您可以使用許可證序號在NetApp Console中啟動 BYOL。


所有NetApp資料服務的授權均透過NetApp Console中的訂閱進行管理。設定 BYOL 後，您可以在控制台中看到該服務的有效授權。

災難恢復的授權是根據受保護的 ONTAP Volume 上託管的資料量來計算。此服務透過將受保護的虛擬機器對應至其 vCenter 資料存放區，來決定哪些 Volume 應納入授權考量。每個資料存放區都託管在 ONTAP Volume 或 LUN 上。ONTAP 針對該 Volume 或 LUN 報告的已使用容量將用於決定授權。Kubernetes 工作負載的授權計算方式相同。

受保護的 Volume 可以主機多個虛擬機器。其中一些可能不屬於災難恢復資源群組。無論如何，該 Volume 或 LUN 上所有虛擬機器所使用的儲存設備都會計入授權的最大容量。


NOTE: 災難恢復費用是基於來源站台上資料儲存的已使用容量，前提是至少有一個虛擬機器或 Kubernetes 資源具有複寫計畫。容錯移轉資料儲存的容量不包含在容量配額中。對於 BYOL ，如果資料超過允許的容量，則服務中的操作將受到限制，直到您獲得額外的容量授權或在 NetApp Console 中升級授權。

如需設定災難恢復授權的詳細資訊，請參閱link:../get-started/dr-licensing.html["設定災難恢復授權"]。

[[how-disaster-recovery-works]]
== 災難恢復的工作原理

災難恢復是可從 NetApp Console 軟體以服務形式（SaaS）環境取得的服務。災難恢復可恢復從內部部署站台複寫到 Amazon FSx for ONTAP 或另一個內部部署站台的工作負載。對於 VMware 工作負載，此服務可自動執行從 SnapMirror 層級、透過虛擬機器註冊到 VMware Cloud on AWS，一直到直接在 VMware 網路虛擬化與安全性平台 NSX-T 上進行網路對應的恢復程序。所有虛擬機器雲端環境均包含此功能。

災難恢復採用 ONTAP SnapMirror 技術，該技術提供高效的複寫，並保留了 ONTAP 永久增量快照的優勢。SnapMirror 複寫可確保應用程式一致性快照副本始終保持同步，並且在容錯移轉後資料可以立即使用。

image:dr-architecture-diagram-70-2.png["災難恢復服務基礎架構的架構圖"]

當發生災難時，此服務可透過中斷 SnapMirror 關係並使目的地站台成為作用中，協助您在另一個內部部署 VMware 環境或 VMC 中恢復 VMware 虛擬機器。

* 該服務還允許您將虛擬機器故障還原到原始來源位置。
* 您可以在不中斷原始虛擬機器的情況下測試災難復原故障轉移流程。此測試透過建立磁碟區的FlexClone將虛擬機器還原到隔離網路。
* 對於故障轉移或測試故障轉移過程，您可以選擇最新（預設）或選定的快照來還原虛擬機器。


*Kubernetes 工作負載*

對於 Kubernetes 工作負載，災難恢復使用 Trident Protect 來保護執行在 Kubernetes 叢集（包括 OpenShift 虛擬化環境）上的應用程式。該服務使用 SnapMirror 來複寫 NetApp Trident 在 ONTAP 儲存設備上配置的持續性 Volume。Trident Protect 將 Kubernetes 保護資料儲存在 AppVault 中，這是一個雲端儲存目標。發生災難時，您可以容錯移轉到目的地叢集，並在災難解決後容錯回復到原始來源叢集。Kubernetes 工作負載的容錯移轉、容錯回復和容錯移轉測試遵循與 VMware 工作負載相同的順序。

*災難復原的組成部分*

Disaster Recovery 使用以下元件：

* * NetApp Console*：用於管理災難復原計畫的使用者介面。您可以使用NetApp Console在本機和雲端環境中建立和管理複製計畫、資源群組和故障轉移作業。
* *Console 代理程式*：在您的雲端託管網路或內部部署 VMware 環境中執行的輕量級軟體元件。它會與 NetApp Console 通訊，並管理內部部署環境與災難恢復站台之間的資料複寫。Console 代理程式安裝在您 VMware 環境中的虛擬機器上。對於 Kubernetes 工作負載，Console 代理程式會以相同的方式與您的 Kubernetes 叢集通訊。
* *ONTAP 儲存設備叢集*：ONTAP 儲存設備叢集是託管 VMware 和 Kubernetes 工作負載的主儲存設備系統。ONTAP 儲存設備叢集為您的災難恢復計畫提供基礎儲存設備基礎架構。災難恢復使用 ONTAP 儲存設備 API 來管理 ONTAP 儲存設備叢集，例如內部部署陣列，以及雲端型解決方案，例如 Amazon FSx for NetApp ONTAP。
* *vCenter 伺服器*：VMware vCenter 是您的 VMware 環境的管理伺服器。它管理 ESXi 主機及其相關的資料儲存。控制台代理程式與 VMware vCenter 通信，以管理本機環境和災難復原站點之間的資料複製。這包括將ONTAP LUN 和磁碟區註冊為資料儲存、重新配置虛擬機器以及啟動和停止虛擬機器。
* *Kubernetes 叢集和 Trident Protect*：對於 Kubernetes 工作負載，Trident Protect 會安裝並註冊在災難恢復所保護的每個 Kubernetes 叢集上。當您將 Kubernetes 叢集新增為站台時，災難恢復會引導您在該叢集上安裝並註冊 Trident Protect。


*災難復原保障工作流程*

當複製計劃分配給資源組時，災難復原會對資源組和計劃中的所有元件執行發現檢查，以確保該計劃可以啟動。

如果此檢查成功，災難復原將執行下列初始化步驟：

. 對於目標資源群組中的每個虛擬機，確定託管 VMware 資料儲存。
. 對於找到的每個 VMware 資料儲存庫，識別託管ONTAP FlexVol volume或 LUN。
. 對於找到的每個ONTAP磁碟區和 LUN，確定來源磁碟區和目標網站中的目標磁碟區之間是否存在現有的SnapMirror關係。
+
.. 如果沒有預先存在的SnapMirror關係，請建立任何新的目標卷，並在每個未受保護的來源磁碟區之間建立新的SnapMirror關係。
.. 如果存在預先存在的SnapMirror關係，請使用該關係執行所有複製操作。




災難復原建立並初始化所有關係後，在每次排程備份時，該服務都會執行下列資料保護步驟：

. 對於每個標記為「應用程式一致的」的 VM，使用 VMware Tools 將受支援的應用程式置於備份狀態。
. 為託管受保護的 VMware 資料儲存的所有ONTAP磁碟區建立新快照。
. 執行SnapMirror更新操作以將這些快照複製到目標ONTAP叢集。
. 確定保留的快照數量是否超過了複製計劃中定義的最大快照保留量，並從來源磁碟區和目標磁碟區中刪除任何多餘的快照。




[[supported-protection-targets-and-datastore-types]]
== 支援的保護目標和資料儲存類型

*支援的資料儲存類型* 災難恢復支援以下資料儲存類型：

* 託管在ONTAP叢集上的ONTAP FlexVol磁碟區上的 NFS 資料儲存庫。
* 使用 iSCSI 或 FC 協定的 VMware vSphere 虛擬機器檔案系統 (VMFS) 資料存儲


對於 Kubernetes 工作負載，Disaster Recovery 可保護透過 NetApp Trident on ONTAP 儲存設備佈建的持續性 Volume。

*支持的保護目標*

* AWS 上的 VMware Cloud (VMC) 以及適用Amazon FSx for NetApp ONTAP
* 另一個基於本機 NFS 的 VMware 環境，配備 ONTAP 儲存設備；或一個本機 FC/iSCSI VMFS 環境
* Amazon Elastic VMware 服務
* Azure VMware Solution 與 NetApp Cloud Volumes ONTAP (iSCSI)（私有預覽版）
* Google Cloud VMware Engine (GCVE) 與Google Cloud NetApp Volumes
* 執行 Trident 管理的 ONTAP 儲存設備（使用 Trident Protect 保護）的 Kubernetes 叢集




[[terms-that-might-help-you-with-disaster-recovery]]
== 可能對您災難恢復有幫助的術語

了解一些與災難復原相關的術語可能會對您有所幫助。

* *資料儲存*：VMware vCenter 資料容器，它使用檔案系統來保存 VMDK 檔案。典型的資料儲存類型是 NFS、VMFS、vSAN 或 vVol。災難復原支援 NFS 和 VMFS 資料儲存。每個 VMware 資料儲存庫都託管在單一ONTAP磁碟區或 LUN 上。災難復原支援位於ONTAP叢集上的FlexVol磁碟區上託管的 NFS 和 VMFS 資料儲存庫。
* *複製計畫*：一組關於備份頻率以及如何處理故障轉移事件的規則。計劃被指派給一個或多個資源組。
* *復原點目標 (RPO)*：發生災難時可接受的最大資料遺失量。  RPO 在複製計劃的資料複製頻率或複製計劃中定義。
* *恢復時間目標（RTO）*：可接受從災難中恢復的最長時間。RTO 定義於複寫計畫中，是指容錯移轉至災難恢復站台並重新啟動所有虛擬機器或應用程式所需的時間。
* *資源群組*：一種邏輯 Container，可讓您將多個虛擬機器、資料儲存或 Kubernetes 資源作為單一單位進行管理。一個虛擬機器一次只能屬於一個資源群組。您可以為每個想要保護的應用程式或工作負載建立一個資源群組。
* *站台*：通常與實體資料中心或雲端位置關聯的邏輯 Container，託管一個或多個 vCenter 叢集或 Kubernetes 叢集以及 ONTAP 儲存設備。
* *AppVault*：對於 Kubernetes 工作負載，這是 Trident Protect 儲存 Kubernetes 保護資料的雲端儲存目標。
* *Trident Protect*：災難恢復用來保護 Kubernetes 應用程式的 NetApp 軟體。
