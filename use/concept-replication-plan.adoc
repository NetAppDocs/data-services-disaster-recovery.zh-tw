= 最佳化 NetApp Disaster Recovery 中的複寫計畫
:hardbreaks:
:allow-uri-read: 
:icons: font
:imagesdir: ../media/use/


[role="lead"]
複寫計畫是災難恢復策略的重要組成部分，它定義了快照頻率、開機順序、網路映射以及故障轉移和故障復原的其他關鍵細節。在 NetApp Disaster Recovery 中建立複寫計畫之前，請確保您了解複寫計畫的運作方式與最佳實務。



[[about-replication-plans]]
== 關於複製計劃

您可以使用單一複寫計畫保護多個虛擬機器、資料儲存區或命名空間。災難恢復會為代管受保護資料資源的所有 ONTAP Volume 建立 ONTAP 一致性群組。



[[resource-planning]]
== 資源規劃

在將資源指派給複寫計畫之前，請先組織您的虛擬機器或命名空間，以盡量減少過度擴張。將需要保護的資源放置在資料儲存區的子集上，並將不需保護的資源放置在不同的資料儲存區子集上。若要在建立複寫計畫之前組織資源群組，請參閱 link:resource-group.html["建立資源組"]。



[[test-failover]]
== 測試故障轉移

建立複寫計畫時，您可以選擇設定獨特的測試容錯移轉對應。

如果您打算在複寫計畫中執行測試容錯移轉，則應提供一組測試容錯移轉對應，以確保在容錯移轉測試期間啟動的虛擬機器不會干擾正式作業虛擬機器。您可以透過為測試虛擬機器提供不同的 IP 位址，或將測試虛擬機器的虛擬 NIC 對應到與正式作業隔離的但具有相同 IP 組態的不同網路（稱為 _bubble_ 或測試網路）來實現這一點。



[[snapshots]]
== 快照

災難復原在來源叢集和目標叢集上維護相同數量的快照。預設情況下，該服務每 24 小時執行一次快照協調過程，以確保來源叢集和目標叢集上的快照數量相同。

以下情況可能會導致來源集群和目標集群之間的快照數量不同：

* 某些情況可能會導致災難復原以外的ONTAP操作在磁碟區中新增或刪除快照：
+
** 如果來源網站上缺少快照，則目標網站上的對應快照可能會被刪除，具體取決於關係的預設SnapMirror策略。
** 如果目的地站台上缺少快照，則根據 SnapMirror 關係的預設原則，服務可能會在下次排程的快照協調過程中刪除來源站台上的對應快照。


* 複製計劃的快照保留計數的減少可能導致服務刪除來源網站和目標網站上最舊的快照以滿足新減少的保留數量。


在這些情況下，災難復原會在下一次一致性檢查時從來源和目標叢集中刪除較舊的快照。或者，管理員可以透過選擇「操作」立即執行快照清理image:icon-horizontal-dots.png["水平點操作選單"]複製計劃上的圖示並選擇*清理快照*。

災難復原每 24 小時執行一次快照對稱性檢查。



[[platform-managed-backups]]
== 平台管理的備份

如果您打算使用平台管理的備份（即 ONTAP 管理的快照），建議您使用 *MirrorAll* 複寫原則。請查看下表，以了解不同 SnapMirror 複寫原則的影響，以及為何 MirrorAll 是建議的選項。

[cols="10,10,80"]
|===


| 原則 | 建議 | 筆記 


| *MirrorAll* | 建議 | 請勿使用 SnapMirror 傳輸快照進行容錯移轉或容錯回復操作。 


| *MirrorVault* .2+| 替代建議 .2+| 請確保在故障轉移或故障復原期間選擇的快照同時存在於來源和目的地 Volume 上。否則，將出現以下錯誤：「Transition to 'snapmirrored' state failed.Reason: No common snapshot found.」請勿使用 SnapMirror 傳輸快照進行容錯移轉或容錯回復操作。 


| *非同步* 


| *MirrorLatest* | _NOT_ 建議 | 此原則導致目的地實際上只有一個用於容錯移轉的通用快照，這對於災難恢復情境來說是不理想的。 
|===


[[disaster-recovery-managed-backups]]
== 災難恢復管理的備份

使用災難恢復代管備份時，以下指引適用於在 NetApp Disaster Recovery 之外建立的 SnapMirror 關係：

* SnapMirror 關係可以支援 MirrorAll、MirrorVault、MirrorLatest 和非同步複寫原則。
* *請勿*為這些關係排程更新，因為它們將由 NetApp Disaster Recovery 服務管理。




[[application-consistent-replicas]]
== 應用程式一致的副本

許多虛擬機器託管資料庫伺服器，例如 Oracle 或 Microsoft SQL Server。這些資料庫伺服器需要應用程式一致的快照，以確保在拍攝快照時資料庫處於一致狀態。

應用程式一致性快照可確保在拍攝快照時資料庫處於一致狀態。這很重要，因為它可以確保資料庫在故障轉移或故障回復操作後能夠恢復到一致狀態。

資料庫伺服器管理的資料可能與託管該資料庫伺服器的虛擬機器位於相同的資料儲存區，也可能位於不同的資料儲存區。下表顯示 NetApp Disaster Recovery 中應用程式一致性快照的支援組態：

[cols="20,20,40a"]
|===
| 數據位置 | 支援 | 筆記 


| 與虛擬機器位於同一 vCenter 資料儲存區內 | 是的  a| 
由於資料庫伺服器和資料庫都位於同一個資料儲存區中，因此在故障轉移時伺服器和資料都會同步。



| 與虛擬機器位於不同的 vCenter 資料儲存區內 | 不  a| 
災難復原無法識別資料庫伺服器的資料何時位於不同的 vCenter 資料儲存體上。該服務無法複製數據，但可以複製資料庫伺服器虛擬機器。

雖然資料庫資料無法複製，但此服務可確保資料庫伺服器執行所有必要步驟，以確保資料庫在 VM 備份時處於靜止狀態。



| 在外部資料來源中 | 不  a| 
如果資料駐留在客戶端安裝的 LUN 或 NFS 共用上，則災難復原無法複製數據，但可以複製資料庫伺服器 VM。

雖然資料庫資料無法複製，但此服務可確保資料庫伺服器執行所有必要步驟，以確保資料庫在 VM 備份時處於靜止狀態。

|===
在計劃備份期間，災難復原會使資料庫伺服器處於靜止狀態，然後對託管資料庫伺服器的虛擬機器進行快照。這可確保在拍攝快照時資料庫處於一致狀態。

* 對於 Windows 虛擬機器，此服務使用 Microsoft Volume Shadow Copy Service （VSS） 與兩種資料庫伺服器類型進行協調。
* 對於 Linux VM，該服務使用一組腳本將 Oracle 伺服器置於備份模式。
